
# Sistem de gestiune a mentenantei auto

The application manages the maintenance history of a vehicle.
It allows users to keep track of completed and pending maintenance operations.

The project is built with React, Vite, React Router and CSS Modules on the frontend, and Node.js with Express on the backend.

## Data model

| Field | Type | Notes |
|---|---|---|
| id | number | Unique positive integer generated by the backend |
| operation | text | Required, maximum 100 characters |
| completed | boolean | Completed or pending, default false |
| type | fixed values | Maintenance, Repair, Inspection |
| description | text | Optional, maximum 500 characters |
| category | relation | Engine, Brakes, Tires, Electrical (planned) |
| user | relation | The owner of the item (planned) |

Allowed values for `type`:

- `maintenance`
- `repair`
- `inspection`

The initial sample data contains five operations:

1. Engine oil change, completed, Maintenance
2. Front brake pad replacement, pending, Repair
3. Tire pressure check, pending, Inspection
4. Air filter change, pending, Maintenance
5. Electrical system check, completed, Inspection

The data is currently initialized inside `backend/src/routes/operatiuni.js`.

## How to run

From Stage 9 onward, the application consists of two separate projects:

- `backend/` - the Express REST API on port 3001;
- `frontend/` - the React application on port 5173.

The old json-server has been removed.

### Install dependencies

From the repository root, install the backend dependencies:

```bash
cd backend
npm install
```

Install the frontend dependencies in a separate terminal:

```bash
cd frontend
npm install
```

### Terminal 1: Express backend

Open a terminal in `backend/` and run:

```bash
npm run dev
```

The development server automatically restarts when backend source files change.

The backend starts at:

`http://localhost:3001`

Check its health endpoint:

`http://localhost:3001/health`

Expected response:

```json
{
  "status": "ok"
}
```

The operations endpoint is:

`http://localhost:3001/operatiuni`

For a normal server start without watch mode, use:

```bash
npm start
```

### Terminal 2: React frontend

Open another terminal in `frontend/` and run:

```bash
npm run dev
```

Open the Vite address, usually:

`http://localhost:5173/`

The frontend communicates with the Express server through `frontend/src/api.js`.

The default API URL is `http://localhost:3001`.

A different API URL can be configured through `VITE_API_URL`, as documented in `frontend/.env.example`.

### Backend environment configuration

The file `backend/.env.example` documents the following settings:

```env
PORT=3001
CORS_ORIGIN=http://localhost:5173
```

The current application uses these values as defaults.

The `PORT` and `CORS_ORIGIN` environment variables can also be supplied when starting the Node.js process.

### Available frontend pages

| URL | Page |
|---|---|
| `/` | Maintenance dashboard and operations list |
| `/operatiuni/:id` | Detail page for a single operation |
| `/despre` | About the application |
| Any other URL | Custom 404 page |

Example detail URL:

`http://localhost:5173/operatiuni/1`

### Verify the frontend

From `frontend/`:

```bash
npm run lint
npm run build
```

### Verify backend installation

From `backend/`:

```bash
npm ci
npm start
```

The backend uses its own `package.json` and `package-lock.json`.

## Stage 2: data logic

Plain JavaScript, no DOM. `mentenanta.js` holds the array and functions that read and change it.

Results are printed in the browser console (F12).

The application data is stored as an array of maintenance operations.

Each operation has a unique id, an operation name, a completed state and a type.

The following functionality was implemented:

- list operation names;
- count pending operations;
- search operations by name;
- add a new operation with validation;
- generate a unique id using the maximum existing id plus one;
- toggle the completed state of an operation;
- delete an operation.

The JavaScript functions do not modify the original array.

Functions that change the data return a new array instead.

## Stage 3: Vite and React project

The application was moved into `frontend/`, using Vite and React.

The files from previous stages were preserved in the `mockup/` folder.

The original maintenance data was placed in the main React component, `App.jsx`.

The application initially displayed:

- the application name;
- the total number of maintenance operations;
- the number of pending operations;
- the maintenance data as raw JSON.

The styles from Stage 1 were reused.

The visual list components were introduced in Stage 4.

## Stage 4: components

The maintenance list is rendered using React components:

- `OperatiuniList` receives the operations array.
- `OperatiuneCard` receives an individual operation through props.

The list is rendered using `map`.

Each operation card uses the operation ID as its React `key`.

An explicit message appears when the list is empty.

The card appearance depends on the operation data and completion state.

## Stage 5: local state and events

The operation list was moved into React state using `useState`.

Each operation can be marked as completed or pending through a controlled checkbox.

Operations can also be deleted from the interface.

State is updated immutably:

- `map` changes the `completed` value;
- `filter` removes an operation;
- the original state array is not modified directly.

The dashboard statistics are calculated from the current list:

- total operations;
- pending operations;
- completed operations;
- maintenance progress;
- number of Maintenance operations;
- number of Repair operations;
- number of Inspection operations.

The application also includes a light/dark theme button.

The current theme is stored in React state and applied through the `data-theme` attribute on the HTML element.

In Stage 5, changes were local to React state and disappeared on refresh. Persistence was added in later stages.

## Stage 6: data from a mock API

Stage 6 introduced a temporary REST API with `json-server`.

Operations were stored in `frontend/db.json` under the resource name `operatiuni`.

The mock API originally ran at:

`http://localhost:3001/operatiuni`

The frontend API requests were centralized in `frontend/src/api.js`.

The `fetchOperatiuni` function used `fetch`, `async` / `await`, `res.ok` and `VITE_API_URL`.

When the main component mounted, `useEffect` fetched the operations.

The initial list was empty, and the interface handled:

- loading;
- successful responses;
- errors when the API was unavailable.

The effect used a cleanup variable named `ignore` to prevent an outdated response from updating an unmounted component.

During Stage 6, checking and deleting operations still changed only local React state.

Server persistence was introduced in Stage 7.

The mock server and its `db.json` file were removed in Stage 9.

## Stage 7: form and validation

Stage 7 introduced a controlled React form and persistent CRUD operations through the temporary REST API.

A form was created in:

`frontend/src/components/OperatiuneForm.jsx`

### Controlled form

The form contains:

- `operation`: required text, maximum 100 characters;
- `type`: Maintenance, Repair or Inspection.

The `completed` field is automatically initialized to `false` for new operations.

Each form field uses React state with `value` and `onChange`.

### Validation

Before submission, the frontend checks:

- the operation name is not empty;
- the operation name does not exceed 100 characters;
- the selected type is valid.

The `trim()` method removes unnecessary spaces.

The form uses `preventDefault()` to avoid a page reload.

Validation errors are displayed directly in the interface.

### CRUD requests

All HTTP requests are centralized in `frontend/src/api.js`.

The application supports:

| Operation | HTTP method | Endpoint |
|---|---|---|
| Read all | GET | `/operatiuni` |
| Read one | GET | `/operatiuni/:id` |
| Create | POST | `/operatiuni` |
| Update | PATCH | `/operatiuni/:id` |
| Delete | DELETE | `/operatiuni/:id` |

React state is updated after successful server responses.

The form submit button is disabled while a request is in progress.

Form input is cleared only after successful creation.

If the request fails, the user sees an error message and the entered values are preserved.

### Data persistence

In Stage 7, changes were saved by json-server.

Successful additions, updates and deletions survived a browser refresh.

Stage 9 replaces json-server with a custom Express API. Changes still survive a browser refresh while the backend is running, but reset when the server restarts.

## Stage 9: own backend with Express

Stage 9 replaces the temporary json-server API with a custom backend written in Node.js and Express 5.

The frontend continues to use the same REST endpoints and data model.

The backend is located in the `backend/` directory, separately from the React frontend.

### Backend structure

The backend contains:

| File | Purpose |
|---|---|
| `backend/package.json` | Dependencies and start scripts |
| `backend/.env.example` | Environment configuration example |
| `backend/.gitignore` | Excludes local dependencies and environment files |
| `backend/src/server.js` | Starts the HTTP server |
| `backend/src/app.js` | Express configuration and middleware |
| `backend/src/validation.js` | Server-side data validation |
| `backend/src/routes/operatiuni.js` | REST routes and in-memory data |

The `app.js` and `server.js` files are separate so the Express application can be imported without immediately starting an HTTP listener.

### Express middleware

The server uses:

- `cors()` to allow HTTP requests from the React frontend;
- `express.json()` to parse JSON request bodies;
- a route handler for unknown URLs;
- centralized error-handling middleware.

CORS allows communication between the frontend on port 5173 and the backend on port 3001.

The accepted frontend origin defaults to:

`http://localhost:5173`

### Health endpoint

The server exposes:

`GET /health`

Expected response:

```json
{
  "status": "ok"
}
```

The endpoint is used to verify that the backend is running.

### REST endpoints

The resource name remains `operatiuni`, matching `tw.json`.

| Method | Endpoint | Description | Success code |
|---|---|---|---|
| GET | `/operatiuni` | Retrieve all operations | 200 |
| GET | `/operatiuni/:id` | Retrieve one operation | 200 |
| POST | `/operatiuni` | Create an operation | 201 |
| PATCH | `/operatiuni/:id` | Partially update an operation | 200 |
| DELETE | `/operatiuni/:id` | Delete an operation | 204 |

The backend generates unique positive numeric IDs.

The API returns JSON responses for reads, creation, updates and errors.

A successful DELETE request returns HTTP 204 without a response body.

### Server-side validation

Input validation is implemented in:

`backend/src/validation.js`

The server validates data independently of the React form.

The `operation` field must be a nonempty string with a maximum length of 100 characters.

The accepted `type` values are:

- `maintenance`
- `repair`
- `inspection`

The `completed` field must be a boolean.

For new operations, `completed` defaults to `false`.

The optional `description` must be text and cannot exceed 500 characters.

The server accepts only known fields and ignores unknown fields such as client-supplied IDs.

For PATCH requests, validation is partial: only submitted fields are checked.

URL IDs are converted to positive integers and validated.

### HTTP response codes

The backend uses the following HTTP status codes:

| Code | Meaning |
|---|---|
| 200 | Successful read or update |
| 201 | Operation created |
| 204 | Operation deleted |
| 400 | Invalid request data or ID |
| 404 | Operation or route not found |
| 500 | Internal server error |

Error responses have a consistent format:

```json
{
  "error": "Operațiunea nu există."
}
```

### Frontend integration

The React components and routing structure remain unchanged.

Only `frontend/src/api.js` requires a functional modification to read the error message returned by the Express backend.

When an HTTP request fails, `request()` reads the server response:

```javascript
if (!res.ok) {
    const body = await res.json().catch(() => ({}));
    throw new Error(body.error || `Eroare server: ${res.status}`);
}
```

The message is displayed in the application.

The frontend continues to support:

- viewing operations;
- adding operations;
- marking operations as completed;
- deleting operations;
- viewing operation details;
- navigation without reloading;
- dashboard statistics;
- light/dark theme.

### In-memory data storage

Stage 9 temporarily stores operations in a JavaScript array inside:

`backend/src/routes/operatiuni.js`

The five automotive examples are loaded whenever the backend starts.

Changes made through POST, PATCH and DELETE survive a browser refresh as long as the backend process is running.

**Important:** Changes are lost when the backend restarts.

Persistent storage with MariaDB will be introduced in Stage 10.

### Removing json-server

The temporary mock API is no longer needed.

The following were removed from the frontend:

- `frontend/db.json`;
- the `api` script from `frontend/package.json`;
- the `json-server` dependency.

`frontend/package-lock.json` was updated using `npm install`.

The application now starts its API from `backend/` rather than `frontend/`.

### Testing the REST API with curl

Start the backend from `backend/`:

```bash
npm run dev
```

Open another Git Bash terminal.

Get all operations:

```bash
curl -s -w '\nHTTP %{http_code}\n' http://localhost:3001/operatiuni
```

Expected HTTP status: `200`.

Get a single operation:

```bash
curl -s -w '\nHTTP %{http_code}\n' http://localhost:3001/operatiuni/1
```

Expected HTTP status: `200`.

Create an operation:

```bash
curl -s -w '\nHTTP %{http_code}\n' \
  -X POST http://localhost:3001/operatiuni \
  -H "Content-Type: application/json" \
  -d '{"operation":"Test din curl","type":"repair","completed":false}'
```

Expected HTTP status: `201`.

With a freshly started backend, the new operation receives ID 6.

Update that operation:

```bash
curl -s -w '\nHTTP %{http_code}\n' \
  -X PATCH http://localhost:3001/operatiuni/6 \
  -H "Content-Type: application/json" \
  -d '{"completed":true}'
```

Expected HTTP status: `200`.

Delete it:

```bash
curl -s -w '\nHTTP %{http_code}\n' \
  -X DELETE http://localhost:3001/operatiuni/6
```

Expected HTTP status: `204`.

Request a nonexistent operation:

```bash
curl -s -w '\nHTTP %{http_code}\n' http://localhost:3001/operatiuni/999
```

Expected HTTP status: `404`.

Send an invalid operation name:

```bash
curl -s -w '\nHTTP %{http_code}\n' \
  -X POST http://localhost:3001/operatiuni \
  -H "Content-Type: application/json" \
  -d '{"operation":"","type":"repair"}'
```

Expected HTTP status: `400`.

Test an empty JSON object:

```bash
curl -s -w '\nHTTP %{http_code}\n' \
  -X POST http://localhost:3001/operatiuni \
  -H "Content-Type: application/json" \
  -d '{}'
```

Expected HTTP status: `400`.

All operations are stored in memory and reset when the backend process restarts.

Stage 10 will replace the in-memory array with persistent MariaDB storage.
